# Known inconsistencies

*Observed disagreements in the reference, collected before anyone decides them.*

Each row is a disagreement between two built rules, or between a rule and the runtime. A row is a
candidate for a decision, never a rule. `pnpm ref lint` and `pnpm ref check` do not treat this file as a concept.

[#670](https://github.com/rcrsr/rill/issues/670) reviews every concept file and decides every row
here. 0.24.0 does not ship until it closes.

## Ids and edges

Every row has an `Id` that is never reused or renumbered, so a decided row leaves a gap. Findings
in [AUDIT.md](AUDIT.md) use `D-nn` ids. The `Affects` column records what deciding the row changes:

| Part | Meaning |
|------|---------|
| Class | `Decision`: the owner chooses the behavior. `Amendment`: the reference contradicts itself or a locked test, the runtime agrees with one side, and only wording changes. `Defect?`: a rule exists, an equivalent form already complies, and the row names no locked test that pins the deviation; a candidate to move to Findings |
| Rules | Each rule the row names, with the rules that cite it. A decision that amends the rule reaches those too |
| With | Rows that are the same decision. Decide them together |
| After | Rows to decide or fix first, because their outcome changes this row's expected result. Transitive |
| Then | Rows whose expected result this decision changes. Transitive |
| See | Rows that touch the same code path or concept without changing this row's expected result |
| Pinned | Locked tests the row names as pinning the runtime's side. A decision against them changes a locked test |

`After` and `Then` are directed and name a specific behavior. Never link two rows only because they
share a concept. When a row is added, decided, or removed, update the rows that name it.

## Adding a row

1. Probe the behavior against `packages/core/dist`, per [CLAUDE.md](CLAUDE.md) "Probing the
   runtime". Put the evidence in the row: the source, the observed result, and the rules involved.
2. Group the row under a `##` heading per topic. Add a heading when no topic fits.
3. Name every concept the row touches in the Concept column.
4. Add the row even when the disagreement sits outside the file you are working on.
5. Give the row the next unused `Id`, and fill `Affects` per "Ids and edges".

## Deciding a row

1. Bring the question to the owner with the rules involved, the evidence, and a proposed amendment.
2. File the issue that records the decision.
3. Write the decided behavior as a `{pending #N}` rule in the owning concept.
4. Remove the row. Remove the heading when no row remains under it.

A defect, where the runtime breaks a rule nobody disputes, is not a row here. While the audit is
open it goes in the [AUDIT.md](AUDIT.md) Findings table; otherwise file it as an issue.
