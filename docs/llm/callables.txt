# rill callables

Closures, fn literals, late binding, typed functions, reflection, dispatch operators, extraction, spread, modules.

## Pipe binding rules

When `->` targets a callable, the runtime decides how to bind the piped value. Two rules, checked in order:

1. **Explicit `$` (manual placement).** If the immediate argument list contains at least one top-level `$`, every occurrence resolves to the piped value. No auto-prepend.
2. **Auto-prepend.** If no top-level `$` is found, the piped value is prepended as the first argument.

Closures stop the scan. A `$` inside a closure literal (`{ ... }`) is late-bound when the closure runs per-element. It does NOT count as a top-level `$`. Sub-expressions ARE scanned, so `$` inside `g($)` does count.

**Zero-parameter callables.** When auto-prepend is selected and the callable declares zero parameters, the piped value is an excess argument and the call halts RILL-R045, the same as `$f(3)`.

| Call form | Effective call | Notes |
|---|---|---|
| `$val -> fn` | `fn($val)` | Auto-prepend |
| `$val -> fn(1, 2)` | `fn($val, 1, 2)` | Auto-prepend |
| `$val -> fn($)` | `fn($val)` | Explicit |
| `$val -> fn(1, $, 0)` | `fn(1, $val, 0)` | Explicit, middle position |
| `$val -> fn(1, $, $)` | `fn(1, $val, $val)` | Both `$` resolve to piped value |
| `$val -> fn(g($))` | `fn(g($val))` | Sub-expr `$` counts |
| `$list -> filter({ $.active })` | `filter($list, { $.active })` | Closure `$` is late-bound |
| `$val -> zero_param_fn` | `zero_param_fn($val)` | Halts RILL-R045 (excess argument) |

A block or string target must read `$`: `5 -> { 3 }` and `5 -> "label"` halt `RILL-P031` at parse time. A list or dict literal target cannot read `$` at its top level: `3 -> list[$, $]` halts `RILL-P030`. A `$` inside a conditional, guard, retry, timeout, or pass body in an argument counts as written, so nothing is prepended. A `$` inside a nested pipe target in an argument, as in `5 -> f(2 -> g($))`, does not count, so the operand is prepended.

This is why `[1,2,3] -> fold(0, { $@ + $ })` works: the list auto-prepends because no top-level `$` appears in `(0, { $@ + $ })`. The `$` inside the closure body is late-bound per element.

## Closure forms

Block-closures (`{ body }`, implicit `$` parameter):

    { $ + 1 } => $inc
    $inc(5)                            # 6
    5 -> $inc                          # 6 (pipe invocation)
    dict[x: { $ * 2 }]                 # dict value is a closure

Function literals (`fn(params):outer { body }`, the body is a block on the same line):

    fn(x) { $x + 1 } => $inc                 # named parameter
    fn(a, b) { $a + $b } => $add             # multiple params
    fn(x = 0) { $x + 1 } => $inc_or_one      # default value; the param type is any
    fn(x: number) { $x + 1 } => $typed       # type annotation
    fn(x: number):number { $x + 1 } => $out  # return type assertion
    fn { $ + 1 } => $by_reads                # typed by the unnamed params the body reads

A default does not infer the parameter type: `fn(x = "d")` gives `x` the type `any`. Write `fn(x: string = "d")` to constrain it. Unnamed params bind `$` and `$@` (at most two), never mix with named params, and carry no default (RILL-P028). `fn()` takes no params, so a body that reads `$` or `$@` halts RILL-P029; use `fn { ... }` instead. The old pipe-delimited function literal and pipe-delimited type literal halt RILL-P012 naming the fn form.

`{ body }` is deferred (function). `( expr )` is eager.

    { $ + 1 } => $fn                   # closure stored
    ( 5 + 1 ) => $x                    # 6 stored

## Late binding

Closures capture scope, not values. Variables resolve at call time.

`$` vs named params:
- Use `$` in inline pipes and loops: `"hello" -> { .upper }`
- Use named params in stored functions: `fn(x) { $x * 2 } => $double`
- `$` is undefined when a stored closure is called later. Always use named params for reusable closures.

## Typed functions

Unnamed typed params (`fn(type) { body }`, `$` is the type-checked input):

    "hello" -> fn(string) { $ -> .upper }       # $ is string, checked at call
    5 -> fn(number) { $ * 2 }                   # 10
    fn(number):number { $ * 2 } => $double      # stored with return type
    5 -> $double                                # 10
    "hi" -> $double                             # RILL-R001: parameter type mismatch

Any type from `types` works. Parameterized:

    fn(list(number)) { $ -> seq({ $ * 2 }) }

`fn` is the type of every function, and `closure` in a type position halts RILL-P012 naming fn. A function type is exact: names, types, defaults, and outer type must all match. A function with an extra defaulted param, or a default the type omits, does not match.

    5 -> :fn                               # halts: not a function
    $double -> :fn(number):number          # passes

Return type assertion (halts with `#TYPE_MISMATCH` on mismatch):

    fn(x: number):string { "{$x}" } => $fn   # asserts string return
    $fn(42)                                  # "42" (passes)

    fn(x: number):string { $x * 2 } => $fn   # mismatch halts at call
    $fn(5)                                   # halts: return type mismatch

## Callable reflection

`.^type.inner` and `.^type.outer` work on every callable type.

    fn(x: number, y: string) { $x } => $fn
    $fn.^type.inner                        # ordered[x: number, y: string]
    $fn.^type.outer                        # any (no return type declared)

    fn(x: number):number { $x * 2 } => $fn2
    $fn2.^type.outer                       # number

`.^type.inner` returns an ordered of param names to types for named params, a tuple of types for unnamed params, and `ordered[]` for `fn()`. `.^type.outer` returns the declared return type (`any` if undeclared). `.^type.defaults` lists only the params that have a default. Works on script closures, built-ins, host functions.

Description shorthand (bare string in `^(...)` expands to `description: <string>`):

    ^("Get weather for city") fn(city: string) { $city } => $weather
    $weather.^description                  # "Get weather for city"
    $weather.?^description                 # true

    ^("Fetch profile", cache: true) fn(id) { $id } => $get_user
    $get_user.^description                 # "Fetch profile"
    $get_user.^cache                       # true

## Dispatch operators

### Dict dispatch (single key)

Pipe a value to a dict to match keys:

    $val -> dict[apple: "fruit", carrot: "veg"]                 # "fruit" if $val is "apple"
    $val -> dict[apple: "fruit"] ?? "not found"                  # default if no match
    $method -> dict[list["GET","HEAD"]: "safe", list["POST","PUT"]: "unsafe"]   # multi-key

Dict keys are strings. A number or bool selector halts `#TYPE_MISMATCH` (`??` does not recover it); convert with `-> string`:

    "1" -> dict[1: "number", one: "word"]              # "number"
    1 -> string -> dict[1: "number", one: "word"]      # "number"
    1 -> dict[1: "number"]                             # halts #TYPE_MISMATCH

A dispatch literal does not read `$` at its top level. A held block reads `$` as the selector. Build from the piped value with a block:

    3 -> { list[$, $] }                                # list[3, 3]
    3 -> list[$, $]                                    # halts RILL-P030

### List dispatch (index)

    0 -> list["first", "second"]                       # "first"
    -1 -> list["first", "second"]                      # "second"
    5 -> list["a", "b"] ?? "not found"                 # OOB fallback

### Hierarchical dispatch (path)

Pipe a list of keys/indexes:

    list["name", "given"] -> dict[name: dict[given: "Alice"]]  # "Alice"
    list[0, 1] -> list[list[1,2,3], list[4,5,6]]               # 2
    list[] -> dict[a: 1]                                       # dict[a: 1] (empty path = unchanged)
    list["a", "missing"] -> dict[a: dict[x: 1]] ?? "default"   # "default"

A path may mix keys and indexes, since `list[1, "a"]` is legal with type `list(union(number, string))`. Property access reaches the same value:

    dict[users: list[dict[name: "Alice"]]] => $d
    list["users", 0, "name"] -> $d                              # "Alice" (mixed path)
    $d.users[0].name                                            # "Alice"

## Extraction operators

Destructure (`destruct<>`):

    list[1, 2, 3] -> destruct<$a, $b, $c>          # $a=1, $b=2, $c=3
    dict[x: 1, y: 2] -> destruct<x: $a, y: $b>     # $a=1, $b=2
    list[1, 2, 3] -> destruct<$first, _, $third>   # _ skips
    tuple[1, 2] -> destruct<$a, $b>                # tuple, positional
    ordered[x: 1, y: 2] -> destruct<x: $a, y: $b>  # ordered, keyed
    $stream -> destruct<$a>                        # stream and iterator halt RILL-R002

Mixing positional and keyed destructure elements is parse error RILL-P026.
A typed element that fails its type halts `#TYPE_MISMATCH`: `dict[a: "x"] -> destruct<a: $q:number>`.

Slice (`slice<start:stop:step>`):

    list[0,1,2,3,4] -> slice<1:3>      # list[1, 2]
    list[0,1,2,3,4] -> slice<-2:>      # list[3, 4]
    list[0,1,2,3,4] -> slice<::-1>     # list[4,3,2,1,0]
    "hello" -> slice<1:4>              # "ell"
    tuple[0,1,2,3] -> slice<1:3>       # tuple[1, 2]

## List spread

    list[1, 2] => $a
    list[...$a, 3]                     # list[1, 2, 3]
    list[...$a, ...$b]                 # concatenate
    list[...($nums -> fan({ $ * 2 }))] # spread expression result
    list[...tuple[1, 2], 3]            # tuple spread: list[1, 2, 3]
    list[...range(0, 3)]               # iterator halts RILL-R002

## Argument unpacking

    tuple[1, 2, 3] -> $fn(...)         # positional spread: $fn(1, 2, 3)
    ordered[a: 10, b: 2] -> $fn(...)   # named spread: keys must match param order
    tuple[...$list, 3] -> $fn(...)     # spread in tuple then into call
    tuple[1, 2, 3] => $args
    $args -> $fn(...)                  # spread stored tuple
    ordered[a: 1, b: 2] => $named
    $named -> $fn(...)                 # spread stored ordered

## Modules

`use<scheme:resource>` resolves through a host-registered scheme resolver.

    use<module:greetings> => $g        # load module
    $g.hello("World")                  # call module member
    use<ext:qdrant.search>             # load extension member

`use<>` returns the resolved value (dict, function, or any rill type). Hosts register resolvers; scripts cannot. A `guard` around `use<>` catches resolution failures only; halts inside the module propagate.

`v -> use<...>` on a host-resolved value calls a callable, selects from a dict or list, or converts through a type; any other value halts `RILL-R002`. A source module's result, even a function, is returned as-is.

See `control-flow` for iterators and lazy sequences.
